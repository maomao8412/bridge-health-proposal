💡 核心思路

GBDT 负责"算分数"，小模型负责"说人话"。两个模型配合使用：GBDT 输出健康评分和异常特征，小模型把这些数字翻译成工程师能看懂的自然语言诊断报告，还能回答巡检人员的专业问题。

1数据准备：盘点你有哪些数据

数据是模型的上限。先把手里的存货盘点清楚，再决定先训什么、怎么训。

1.1 三类核心数据资产

📊

传感器时序数据

位移/应变/温度/振动
高频、海量、数值型

📝

巡检记录文本

日常巡检/定期检测报告
半结构化、有模板

📷

桥梁图像

人工拍照/无人机巡检
裂缝/锈蚀/病害

1.2 不同数据的用途和优先级

数据类型 适合训练什么能力 加工难度 优先级
巡检记录/检测报告 诊断问答、报告生成、维修建议 ⭐⭐ 中等 P0 最高
维修案例/历史处理记录 故障排查、方案推荐 ⭐⭐⭐ 较难 P0 最高
传感器异常事件记录 异常诊断、趋势分析 ⭐⭐⭐ 较难 P1 较高
桥梁技术文档/规范 知识问答、规范查询 ⭐ 简单 P1 较高
桥梁图像/视频 视觉识别（需要多模态模型） ⭐⭐⭐⭐ 难 P2 后续
⚠️ 建议

先从巡检记录和维修案例入手。这两类数据最容易转成问答对，微调后效果最明显，能最快看到价值。传感器数据和图像数据可以后面再搞。

2数据处理：把原始数据变成问答对

原始数据不能直接喂给模型，需要加工成「指令-回答」格式的训练数据。这一步决定了微调效果的上限。

2.1 巡检记录怎么变问答对

巡检记录一般包含：时间、桥梁、部位、病害描述、处理建议。从中提取出「问题→答案」的配对：

原始记录 转成问答对
部位：3#墩支座
病害：钢板锈蚀，面积约0.5㎡
建议：除锈防腐，定期观察 		Q: 支座钢板锈蚀了怎么办？
A: 支座钢板锈蚀应进行除锈防腐处理，并定期观察锈蚀发展情况。
部位：箱梁底板
病害：纵向裂缝，宽0.3mm，长1.2m
建议：灌胶封闭，观测发展 		Q: 箱梁底板出现0.3mm宽的纵向裂缝怎么处理？
A: 箱梁底板0.3mm纵向裂缝需先检测深度，表面裂缝可灌胶封闭处理，处理后定期观测是否继续发展。

2.2 数据格式规范

统一存成 JSON 格式，每条包含 instruction（问题）、input（补充信息，可空）、output（答案）：

{
  "instruction": "支座钢板锈蚀面积0.5平米，严重吗？怎么处理？",
  "input": "部位：3#墩支座，桥梁类型：连续梁桥",
  "output": "支座钢板锈蚀面积0.5㎡属于轻度锈蚀，暂不影响结构安全。建议：1）除锈防腐处理；2）每季度观察一次；3）如锈蚀面积扩大，安排专项检测。"
}

2.3 数据量建议

  • 起步阶段：50~100条 — 能看到明显的领域倾向，适合验证可行性
  • 可用阶段：300~500条 — 常见问题都能答得不错，可以内部试用
  • 实用阶段：1000~3000条 — 覆盖面广，回答稳定，可对外服务
  • 高质量 > 大数量 — 100条精心打磨的数据 > 1000条粗制滥造的数据

2.4 数据增强技巧

数据不够时，可以用这些方法扩充（但要保证质量）：

  • 换问法：同一个答案，写3~5种不同的问法（"怎么办""怎么处理""咋整""处理方案是什么"）
  • 换场景：把"支座锈蚀"换成"梁底锈蚀""墩柱锈蚀""护栏锈蚀"等不同部位
  • 递进式：做简单→中等→详细三个层级的回答，适应不同需求
  • 用大模型生成：用GPT/Claude等大模型批量生成问答对，人工抽检质量
❌ 数据质量红线

1）不要让模型学错误的知识——所有回答必须符合桥梁工程规范，错误的答案会被模型学进去
2）不要全是一个语气和长度——数据多样性越好，模型生成越自然
3）不要重复数据太多——重复超过3次的样本会导致过拟合

3模型微调：LoRA 训练实操

用 LoRA（低秩适配）做微调，只训练模型不到万分之五的参数，CPU就能跑，成本极低。

3.1 环境准备

需要安装的 Python 库：

pip install transformers torch peft datasets modelscope xxhash

3.2 下载基础模型

用阿里 ModelScope 国内源下载 Qwen2.5-0.5B-Instruct（约942MB）：

from modelscope import snapshot_download
model_dir = snapshot_download(
    'qwen/Qwen2.5-0.5B-Instruct',
    cache_dir='./model_cache'
)

3.3 训练脚本核心代码

LoRA 配置的关键参数：

from peft import LoraConfig, get_peft_model, TaskType

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,                    # 秩，越大能力越强，但越容易过拟合
    lora_alpha=16,           # 缩放系数，通常设为 2*r
    lora_dropout=0.05,       #  dropout 防止过拟合
    target_modules=[         # 要加 LoRA 的层
        "q_proj", "k_proj", "v_proj", "o_proj"
    ],
    bias="none",
)

3.4 关键超参怎么调

参数 推荐值 调大了会怎样 调小了会怎样
r（秩） 8~32 能力强但易过拟合，参数量大 学得浅，但不容易过拟合
learning_rate 1e-4 ~ 3e-4 收敛快但可能震荡 稳但学得慢
num_train_epochs 5~15 过拟合风险大 学不充分
batch_size 2~8 训练稳但慢，显存不够 快但波动大
💡 怎么判断训练好了

看 loss 曲线：如果 loss 一直在下降，说明还在学；如果 loss 不再降了（平台期），就可以停了。 一般 10 个 epoch 左右足够，太多会过拟合——模型只会背训练数据，不会举一反三。

3.5 训练输出产物

LoRA 微调只保存小矩阵权重，文件很小：

  • adapter_config.json — LoRA 配置
  • adapter_model.safetensors — LoRA 权重（通常只有几 MB）

使用时把它加载到原模型上就行，不需要重新保存整个模型。

4.2 必测的对比问题

  1. 训练集中有的问题 — 检验模型有没有学到（应该答得很好）
  2. 训练集没有但同领域的问题 — 检验泛化能力（应该也能答）
  3. 领域外的问题 — 检验模型有没有"忘本"（通用知识还在不）
  4. 陷阱题/反常识题 — 检验模型会不会胡说（不知道就说不知道）

4.3 效果不好怎么排查

现象 可能原因 解决方法
回答跟没调差不多 训练不够 / 学习率太小 多加几个 epoch，或调大 lr
只会背标准答案，换个问法就不会 过拟合了 减少 epoch，增加数据多样性，增大 r
回答开始胡说八道 训练数据有错误 检查训练数据质量，清洗错误样本
回答特别简短/不完整 训练数据答案都太短 增加长回答的数据，调大 max_new_tokens

5模型部署：做成 API 服务

模型训好了，要封装成服务，让你的平台能调用。推荐用 FastAPI 做轻量服务。

5.1 最简部署方案

pip install fastapi uvicorn peft transformers

服务端核心代码结构：

from fastapi import FastAPI
from pydantic import BaseModel
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

app = FastAPI()

# 启动时加载模型（只加载一次）
MODEL_PATH = "./models/qwen-0.5b"
LORA_PATH = "./lora_output/final_lora"

tokenizer = AutoTokenizer.from_pretrained(MODEL_PATH)
base_model = AutoModelForCausalLM.from_pretrained(MODEL_PATH)
model = PeftModel.from_pretrained(base_model, LORA_PATH)
model = model.merge_and_unload()  # 合并权重加速推理

class ChatRequest(BaseModel):
    question: str
    temperature: float = 0.3
    max_tokens: int = 512

@app.post("/api/diagnose")
async def diagnose(req: ChatRequest):
    messages = [{"role": "user", "content": req.question}]
    text = tokenizer.apply_chat_template(
        messages, tokenize=False, add_generation_prompt=True
    )
    inputs = tokenizer(text, return_tensors="pt")
    
    outputs = model.generate(
        **inputs,
        max_new_tokens=req.max_tokens,
        temperature=req.temperature,
        do_sample=True
    )
    response = tokenizer.decode(
        outputs[0][inputs.input_ids.shape[1]:],
        skip_special_tokens=True
    )
    return {"answer": response}

启动服务：

uvicorn server:app --host 0.0.0.0 --port 8000

5.3 硬件要求和性能预估

部署方式 硬件配置 推理速度 并发能力 成本/月
CPU 部署 4核8G ~15 token/s 1~2 并发 ~200元
GPU 部署（推荐） T4 / 3090 单卡 ~80 token/s 10~20 并发 ~1500元
量化部署（INT4） 4G显存即可 ~50 token/s 5~10 并发 ~800元
✅ 推荐起步方案

先 CPU 部署跑通流程，验证业务价值。用户量上来了再上 GPU。4核8G的云服务器， Qwen-0.5B 模型 CPU 推理大概 15 token/s，生成一份200字的诊断报告约10秒， 对于桥梁监测这种低频场景完全够用。

6平台集成：嵌入健康监测系统

模型服务跑起来之后，要和你现有的健康监测平台对接，让用户在日常工作中就能用。

6.1 三个集成场景（从易到难）

场景一：AI 诊断助手（侧边栏对话）

在平台里加一个 AI 对话入口，工程师遇到问题随时问：

  • 接入方式：前端加个聊天窗，后端调用 /api/diagnose 接口
  • 开发量：1~2 天
  • 用户：巡检人员、桥梁工程师

场景二：自动生成诊断报告

每次传感器数据更新后，自动调用模型生成诊断分析，附在健康评分旁边：

  • 接入方式：GBDT算完分数后，同步/异步调用 /api/bridge/diagnosis-report
  • 开发量：3~5 天
  • 展示位置：桥梁详情页 → 健康状态卡片

场景三：智能巡检辅助

巡检人员上传照片和记录，AI 自动分析并给出处理建议：

  • 接入方式：巡检记录提交时触发 AI 分析，返回建议写入数据库
  • 开发量：1~2 周
  • 需要图像识别能力（后续扩展）

6.2 前后端对接方式

方案 实现方式 优点 缺点
直接 HTTP 调用 平台后端直接请求 AI 服务 简单直接 耦合紧，模型挂了平台也受影响
消息队列（推荐） 平台发消息到 MQ，AI 服务消费，结果写回 解耦、可异步、可重试 多了一层中间件
定时任务拉取 AI 服务定时扫描待分析数据 最简单，不需要改平台 有延迟，实时性差

6.3 上线前的安全检查

  • 输出审核：模型可能胡说，关键诊断建议要不要人工复核？建议初期所有 AI 结论都标注"AI 生成，仅供参考"
  • 限流保护：防止频繁调用把服务打爆
  • 日志记录：所有问答都要存日志，出了问题能追溯
  • 反馈机制：用户可以给 AI 回答点赞/点踩，收集数据持续优化

常见问题

0.5B 模型会不会太小了，回答质量行不行？
在通用聊天上确实不如大模型，但在垂直领域微调后效果很好。因为它把有限的"脑容量"全部用在了你的专业领域上。 桥梁健康监测这种专业场景，知识范围相对固定，0.5B~1.8B 足够了。如果以后觉得不够，可以无缝升到 1.8B 甚至 7B，训练流程一样。
没有标注数据怎么办？能自动生成吗？
有几种方法：1）用大模型（GPT-4、Claude 等）根据你的巡检记录和技术文档批量生成问答对，然后人工抽检； 2）从历史检测报告、维修记录中自动提取；3）先上线一个"空壳"AI助手，收集真实用户问题，再人工标注。 建议先用方法1快速起步，有真实数据后不断迭代。
为什么选 LoRA 而不是全量微调？
三个原因：1）成本低——只训万分之五的参数，CPU 就能跑； 2）不毁原模型——LoRA 权重是独立的小文件，想用就加载，不想用就用原模型； 3）方便迭代——不同领域、不同桥梁可以各训一个 LoRA，按需切换。 全量微调只有在你有几十万条数据且算力充足时才考虑。
模型会不会给出错误的诊断建议？出了事故谁负责？
这是一个必须面对的问题。建议：1）AI 定位为"辅助工具"，所有结论标注"AI生成，仅供参考，最终以工程师判断为准"； 2）高风险的判断（比如是否限载、是否封桥）不要让 AI 决定，只提供分析； 3）建立人工审核机制，重要报告需工程师签字； 4）持续收集 badcase，不断优化模型，降低错误率。
模型要多久更新一次？
初期（前3个月）：每2~4周更新一次，因为有很多新数据和 badcase 需要消化； 稳定期：每1~3个月更新一次，主要是加入新的案例和场景； 应急更新：发现严重错误或新增重要病害类型时，随时小版本更新。 LoRA 的好处就是更新快——新数据来了，几十分钟就能训出一个新版本。
